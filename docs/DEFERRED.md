# Direction and Deferred

The developer's standing decisions about what gets built, and the queue of
what is left. When another doc disagrees with this one, this one wins, and
the other doc is updated to match. Out-of-scope ideas land here, never in
code. A row is **removed when it ships**: this is a queue, not a log (git
history has every removed row).

## Direction

- **Shared code, not a starter kit** (decided 2026-09-28, shipped as 3.0).
  The foundation-owned layer is the npm package
  `@tristan2828/ui-foundation`, and apps upgrade by bumping its version. The
  template is copied once, and what it copies is the app's own
  ([`ARCHITECTURE.md`](ARCHITECTURE.md) "Why shared code"). Generic changes
  found in an app are raised here and released, not kept as local variants.
  That is the path a fix takes to every app.
- **Two tracks** (decided 2026-09-20, while building the Game List app).
  *Design language* grows freely and does not wait for a second app or a
  second use: tokens, semantic tones, `Badge` and variant styles, cell
  patterns, typography, density, themes. *Structure* stays need-driven,
  built against a real app's actual screen and not in advance: composites,
  new entry points or exports, backend, auth, infrastructure. Why the
  split: design language is cheap to review by looking at results, and it
  is exactly what an app can't get right alone (contrast, both themes,
  consistency). Structure is where "building forever" is the real risk.
- **Configuration grows from real forks.** A new prop or slot on a
  composite is structure: it is added when an app needs the variation, not
  in advance. Every one so far (`AppShell`'s `nav`/`sidebarExtra`/
  `defaultSidebarOpen`, `EntityForm`'s `danger`, `LoginRoute`'s
  `registerPath`) replaced a fork in Game List.
- **Polish is wanted.** The v1 "doesn't need to be good, needs to be
  reusable" stance was a ship guard, not a design position. Now that a real
  app exists, design-language work is not capped.
- **Review model.** The developer reviews *results* (the running app,
  options pages, screenshots), not every line. The mechanical gates are the
  safety net, and the goal is a foundation strong enough that line-by-line
  review isn't needed.
- **Unchanged:** the Hard Rules (semantic tokens only, shadcn before
  hand-rolling, gateway boundaries, the dependency allowlist). Every
  design-language addition ships with axe contrast coverage in both themes.

## Deferred

| Item | Revisit when |
|---|---|
| Sharing the backend. `template/backend/` is copied into each app and diverges from then on, so a backend fix (auth, the deploy checks, the SPA fallback) reaches no app on its own | Two apps need the same backend fix, or a second app keeps the reference backend. Then decide between a Python package for the auth/deploy/SPA layer and a documented patch routine |
| **Passkeys (WebAuthn) as the second step.** 4.0's second step is TOTP: stdlib only, any authenticator app. Passkeys need a library and a browser ceremony per device | Someone wants to sign in without typing codes, or an app's users can't be trusted to keep recovery codes. Build it on the same second step (`/auth/login` 202, a pending sign-in), with the library's case in `BLOCKERS.md` first |
| **Turning TOTP on from the app.** Today `scripts/enable_totp.py` does it, run by whoever has the server; there's no settings screen with a QR code, and no way for a user to see or replace recovery codes | An account holder needs to turn it on (or replace a lost phone) without the server's operator, or self-service registration is on. Then a settings screen under a session, confirming one code before saving, as the script does |
| **Encrypting the TOTP secret at rest.** `users.totp_secret` is stored as is (checking a code needs it), so a database dump holds every secret; `deploy.md` says to encrypt backups instead | The database or its backups are held where encryption of the dump can't be relied on (a third party with dump access). It needs a crypto dependency and a key from the environment, so it's a decision for the developer |
| **Error reporting's duplicate and per-session counts live in each worker's memory** (`app/routers/client_errors.py`). A restart forgets them, and with several workers each counts its own, so a session can send up to `CLIENT_ERRORS_PER_MINUTE` per worker | A deployment runs several workers and a flood of browser reports is a real cost. Then count in the database, as the sign-in limits do |
| **Error reports carry no breadcrumbs or request context** beyond the route pattern, method and status: no "what the user did before", no performance traces. That's deliberate for privacy, and it's what a stdlib sender can do | A real bug can't be found from what a report holds. Then decide what more is safe to send (screen names, say) before adding anything |
| Additional themes | The developer wants a distinct look; the two-layer tokens already support it. Still no theme-switcher UI (see Excluded) |
| TypeScript 7 (native compiler) | typescript-eslint, openapi-typescript and Storybook's react-docgen-typescript all support it. TS 7's package exposes no classic JS API, and all three are built on that API. The tsconfigs are already TS 7-clean. When revisiting, drop the `openapi-typescript` → `typescript` entry in the `overrides` of the root and template `package.json` once openapi-typescript's own peer range covers the installed TypeScript |
| Read-only entity path in the playbook: a list and a view with no create, edit or delete. The view itself shipped in 3.10 (`EntityView`); the playbook still always builds the form and the view's Edit and Delete | The first real app needs an entity people only read. Build it against that screen: likely `Screens: list, view` in the plan, dropping the form, its routes and the view's actions |
| Rich text: inside a block the person edits, the editor's own Markdown style applies (a table edited gets padded cells, `*`-style marks, a reference link in that paragraph becomes inline; its definition is kept). Every untouched block is kept as written (`markdown-merge.ts`) | An app's notes rely on reference links or hand-aligned tables, and an edit to one block rewriting its formatting is a real complaint. Then merge one level deeper (list items, table rows) the way top-level blocks are merged |
| Rich text: inside a list item, Tab and Shift+Tab indent and outdent the item (Milkdown's list keys), so from a list item the keyboard leaves the text only once the caret is out of the list (or with Esc, editing in place). Not a trap, but not the page's usual Tab either | A keyboard user reports it. Options: Esc then Tab leaves (as code editors do), or Indent/Outdent toolbar buttons and Tab always leaving |
| **Rich text: images and uploads.** Showing an image by URL is the editor's part (Markdown `![alt](url)`, alt text required). Uploading is mostly backend: an endpoint, file storage, size and type limits, and serving files safely (an uploaded SVG or HTML file can run script on the app's own domain), all in the copied-in backend | An app has a screen that needs attachments. Decide storage first (disk, object storage, the database) and how files are served, then the editor's upload hook (`@milkdown/kit` `plugin/upload`) |
| **Rich text: a note with an image can't be edited.** The editor drops images when it loads (`![alt](url)` isn't shown at all, found 2026-10-06 while fixing the merge for padded tables), so any edit to such a note refuses to save: the merge keeps the image's block as written and the guard sees it isn't what's on screen. Refusing is deliberate, since writing the editor's version would delete the image. Before 3.16.2 this was the same refusal | An app's notes hold images (imported from another tool, say) and the refusal is a real complaint. Then show images in the editor (an image node view; the first half of the row above) |
| **Rich text: Notion's table handles.** Tables (3.21) add rows and columns from the Table menu, Tab and the edge bars, but there's no handle on a row or a column to drag it elsewhere or open a menu for just that row (Milkdown has `moveRowCommand`/`moveColCommand`), no column widths (GFM can't store them) and no line break inside a cell (GFM can't either) | Someone reorders rows often enough that cut and paste is a complaint. Then a hover handle per row and column (a node-view widget, as the bars are) with a menu, keyboard reachable through the Table menu |
| **Rich text: a callout's own icon or colour.** Callouts (3.21) are GitHub's five kinds, each with a fixed icon and tone; Notion lets a callout take any emoji and colour. GitHub's syntax has no room for either, so it would need a syntax of our own (and other renderers would stop showing it as a callout) | A real note wants a kind the five don't cover |
| **Rich text: Notion keys with no Markdown behind them.** Notion's toggle list (Ctrl+Shift+7) and underline aren't offered: Markdown has neither, and the editor never writes HTML | A real need for either. A toggle list could be `<details>`, which is HTML and refused today |
| **The template's notes aren't always editable.** 4.4's `alwaysEditable` (the notes are the editor, no click to open) is in Storybook (`app/EntityView` Autosave) and `e2e/entity-view.spec.ts`; Widget's Description uses `autosave` alone. Always editable shows the editor at rest, so a link in the notes can't be followed (the editor has no "open link"), and the template's view specs check the read view (`widget-view.spec.ts`: headings, links opening in a new tab) | The developer wants the template's Description always editable, or an app adopts it and asks to follow links. Then a way to open a link from the editor (Ctrl/Cmd+click, or a small popover on the link, checked with `linkHref`), and move those specs to the read-only path |
| An open `Select` or `MultiReference` list was never axe-checked on the form. Editing in place checks both open: the in-place Status is non-modal, and a typed combobox hides the page from screen readers by design (the ARIA combobox pattern), which axe reads as hidden focusable content (`e2e/a11y.spec.ts` says why each rule is off) | A screen-reader pass on the form, or axe adds a rule the open lists fail |
| Notion API as a data source: a thin backend that serves `openapi.yaml` from a Notion database instead of Postgres (`consuming.md` compares the two) | A real project picks Notion as its source of truth. Build it against that project's database and property types |
| `DataTable` `meta.align: 'right'` for number and currency columns. Today only `'center'` exists, so `cell-patterns.md` pattern 11 keeps numbers left-aligned with `tabular-nums` | A real number column wants right alignment. It's a small change (header and cell both read `meta.align`), but it's a prop, so it waits for that column |
| A yes/no that can also be unset (three states: yes, no, not set) | A real plan needs "not answered" to differ from "no" |
| An **`icon` field type**: a single choice whose values are icon names from a fixed set of Lucide icons. On the form a `Select` whose trigger and options show the icon and its label; elsewhere the icon, tinted with the record's colour slot. To ship: the plan template's `icon` type, an `add-an-entity.md` step (the enum in `openapi.yaml`, the value → Lucide component map in one file, the `Select`, a migration with a CHECK on the values, a backfilled default for existing rows and a `COMMENT ON COLUMN` naming the set), and an icon on the template's WidgetCategory as the worked example (which would also make Widget's Extra Categories the worked example of cell pattern 4's multi-value variant). One app built this for itself (3.14 shipped how such icons display: pattern 4's variant) | A second app plans an icon field. Build it from that plan, with the first app's map, Select and migration to compare against |
| **A labelled deployment** (a staging copy that should say "Staging data"). `APP_ENV=production` refuses to start with `DATA_LABEL` set (3.19), so today a label only exists off production settings | An app deploys a second, non-production copy. Then decide between a deploy check that accepts a label when it's an explicit non-production one, and staging running without `APP_ENV=production` |
| **A tick sent while a move of the same list is saving can tick the neighbour.** A quick-action tick (`ChecklistItem` in the template) changes the item *at its position* in the record's latest list; a move or remove from the list edited in place (3.25) is saved before it, so by then a different item may sit there. The list's own changes find their item by content (`locate` in `editable-list.tsx`); the tick doesn't. The window is the move's round trip, and the move's buttons wait while it saves, but the box doesn't | Someone reports a tick landing on the wrong item. Then have quick-action ticks find the item the way the list does (by its content at the time of the click), in the template and the playbook's copy of it |
| **The template has no small entity edited in its rows** (3.26). The pattern and its code are in cell pattern 18 ("In a table's rows") and Storybook `app/DataTable`, but the playbook has no reference file to copy for `Screens: list, edited in the row`, and nothing exercises it against a real backend. A WidgetCategories screen would be the natural one, but it needs POST/PATCH/DELETE `/widget-categories` in the contract, mocks and backend | The first app builds a small entity this way, or a playbook run on such a plan goes wrong. Then add the template's own example (contract, backend, table, specs) and a reference-files row |
| **A failed logout doesn't say so.** Since 3.27.2 a logout the server doesn't confirm (network down) still ends the session on screen and lands on `/login`, silently. The server's session may still be open, so a reload can sign the person back in. Saying so needs a notice carried to `/login`: `AppShell`'s `Toaster` unmounts with the shell | Someone is surprised to find themselves still signed in, or an app is used on shared computers. Then a notice on `/login` (router state, or a `Toaster` outside the shell) |
| **The package's own axe specs don't wait for a popup to finish opening.** `expectNoAxeViolations` waits out transitions since 3.27.4 (the template's phone Filters sheet failed CI mid-fade), but `packages/ui-foundation/e2e/` builds `AxeBuilder` itself straight after opening menus, tooltips and the link box (`rich-text-editor.spec.ts`, `data-table.spec.ts`, `storybook-visual.spec.ts`), and those fade in too | One of them fails on contrast in CI with colours that pass once open. Then give them the same wait (the package's e2e can't import its built `/testing` entry point the way an app does, so likely a shared helper in `e2e/`) |
| **Switching density from the UI.** `data-density` (3.28: `compact`, `comfortable`, `large`) is a CSS choice an app makes in its own markup; there's no setting, toggle or remembered preference for it. A control for it would be structure (a prop, a hook, somewhere to keep the choice) | An app wants people to switch density themselves, e.g. one screen used both at a desk and from the couch. Build it against that screen |
| **`large` doesn't grow containers or container-query thresholds.** `max-w-*` containers and `@container` breakpoints (`--container-*`) keep their widths under `data-density="large"`, on purpose: they decide layout, and growing them would change it. So a screen inside `max-w-xl` fits about a fifth fewer characters per line at `large` | A real screen at `large` reads as cramped inside its container. Then decide per container whether it's layout (keep it) or a reading measure (grow it with the density) |
| **Hub page composites:** a nav tile grid (large icon tiles linking to a module or an external page) and a stat tile (a number with a label, an optional trend and a tone). The widget card shipped in 3.30 (`WidgetCard`, lists only); the first hub's tiles are plain `Card`s | An app builds a hub or dashboard screen that needs them |
| **Signing in from the MCP approval page returns to it.** `/oauth/authorize` with no session shows "Sign in first" and a link to `/login`; after signing in the person has to connect again from the chat, because `LoginRoute` returns only to router state (`returnPath`), never a query parameter | Someone finds the second connect confusing. Then `LoginRoute` accepts a `next` path (the same in-app-path check `returnPath` has), and the approval page links to `/login?next=…` |
| **Seeing and ending MCP connections in the app.** A person ends one with SQL on `oauth_grants` (`docs/deploy.md` "AI chats (MCP)"), and the audit log is read with SQL too | An app has more than one person approving chats, or someone asks "what is connected?". Then a settings screen over a small authenticated API for grants and the log (contract, mocks, backend) |
| **MCP tools for bulk changes, and for deleting for good.** Chats `delete` (soft only) and `restore` one record per call (#137); there is no bulk call and no hard delete | A real app needs a chat to remove or reshape many records, or to erase one for good, and a log plus the approval page is judged enough. Then add it per entity, off by default, with a confirm step the chat can't skip |
| **MCP audit entry written in the same transaction as the write.** The router functions commit themselves, so the log row follows in a second commit; a crash between them leaves a change unlogged | The log is relied on as proof. Then the entity functions take a session they don't commit, and the tool commits both together |
| **Scheduled jobs have no screen.** `GET /api/jobs` and `POST /api/jobs/{name}/run` (4.7) are in the contract, but nothing in the template shows them, and there are no MSW handlers for them | An app wants to see its jobs or run one from the UI. Then a screen over the two endpoints (mocks, gateway, a small table with a Run now action), which is also when the 409 above needs its `AppError` kind |
| **Grouped rows: collapsing a group, grouping by more than one key, a whole group's summary.** 4.8's `groupBy` heads runs of rows on the page; `groupSummary` sees only the page's rows of a group split across pages | A real screen asks for a collapsible group or two levels, or a group's total that must cover every page. A total across pages comes from the API (a field per group), not from the table |
| **A list-like table can't say which column takes the width.** `header={false}` tables (4.8) look best with the thumbnail inside the title's cell, because `DataTable` has no column width (`meta.align` is the only column meta) and the table shares spare width across columns | A real list needs a separate narrow column (a checkbox, an avatar). Then a `meta.width` (`'min'`, the cell as narrow as its content) |
| **`AppShell`'s version entry doesn't show the schema.** `build-info.json` carries `schema` since 4.9 (#149), but the sidebar shows only the commit and PR; showing the revision too needs it in `import.meta.env` and a field on `AppShellVersion` | Someone checking a deploy wants the revision on screen rather than in `/build-info.json` |
| **`npm run verify` has no low-memory mode.** Its Playwright runs use the default worker count, which crashed workers on a 16 GB Windows machine (2026-10-19); running the gates by hand with `--workers=1` passed (`ARCHITECTURE.md` "Rules learned the hard way") | It happens again, or someone else develops here on a smaller machine. Then honour a `PW_WORKERS` variable in both Playwright configs (`workers: process.env.PW_WORKERS`), or a `verify:low-mem` script that runs the stages in sequence |
| **`data-table.spec.ts` "loading, empty and error keep the width it had loaded" flakes**: off by ~16px (a scrollbar's width) in 2 of 10 repeats on `main` (seen 2026-10-19 while verifying #158/#159), passing on rerun | It fails CI, or once more locally. Then wait for the state's layout to settle (or measure with the scrollbar gutter fixed) before comparing widths |
| Row virtualization | A table exceeds ~5k rows |
| `AppError` kinds for 403 (`forbidden`) and 409 (`conflict`); both render as the generic `server` error today | A screen calls an endpoint that returns either. Only `POST /jobs/{name}/run` (4.7) returns one, a 409 while the job runs, and no screen calls it; another user's widget is a deliberate 404, and a duplicate email is a 422 |
| Dependency-allowlist enforcement for `backend/pyproject.toml`, mirroring `ui-foundation check-deps` on the npm side | The backend gains a second contributor or session where an unreviewed Python dependency is a real risk |
| **The `<nav>` landmark doesn't contain the nav at phone width.** `AppShell` wraps `<Sidebar>` in `<nav aria-label="Primary">`, but below the mobile breakpoint the sidebar renders into a Sheet portaled to `document.body`, so the landmark is empty there. axe doesn't flag it and the links are reachable and labelled, so this is a semantics quirk. The a11y suite reads the links from the sheet on mobile | `AppShell`'s nav markup changes for another reason, or a screen-reader pass on a phone is actually done. Confirm first how it reads in a real mobile screen reader |
| **A new app's first `npm install` writes a lock `npm ci` rejects.** `create-app.sh` repairs it (3.9.0: `npm ci`, then one more `npm install`), but the cause is upstream and still there at 3.16.0, on npm 10.9.4 and 11.7.0. The first install hoists eslint's `ajv` 6 and `ajv-formats` 3 to the root, which breaks `@hookform/resolvers`' *optional* peers (`ajv ^8`, `ajv-formats ^2.1.1`). `npm install` accepts that and `npm ci` rejects it; the second install hoists `ajv` 8 and nests eslint's copy. Inferred to be npm's handling of optional peers, not this repo's. No small fix here: `ajv` can't be overridden globally (eslint needs 6), and a lockfile shipped with the template wouldn't match the version `create-app.sh` writes | The guard's second `npm install` also fails, an app's own later `npm install` writes a lock `npm ci` rejects, or an npm release changes this (check: drop the repair step locally and run `scripts/consume-test.sh --install-only`) |
| **Concurrent `check-backend-postgres.sh` runs share :8000.** Since 4.4.1 each checkout's Postgres is its own, but uvicorn still listens on :8000 and the real-API Playwright run and `check_mcp_live.py` call it there, so two checkouts running the check at the same moment collide | Two checks really do run at once (parallel agent sessions). Then the API port is chosen like Postgres's and passed to Playwright's base URL, the Vite proxy and `MCP_PUBLIC_URL` |
| **`check-backend-postgres.sh` needs Docker.** It deliberately ignores `DATABASE_URL` and always starts the `docker-compose.yml` Postgres, so its test users and migrations never land in a real database. Claude Code cloud sessions have no Docker, so there it can't run (3.9.0's migration was checked against a local `initdb` Postgres by hand instead) | A backend change has to be verified where Docker isn't available. Then add an explicit opt-in for a throwaway database (a separate variable, never `DATABASE_URL` or `backend/.env`), not a fallback |
| **Apps don't get the cloud session hook.** This repo's `.claude/hooks/session-start.sh` (npm install, the backend venv, the Playwright browser mapping) lives at the root, outside what `sync` writes, so an app worked on in a Claude Code cloud session hits the same browser-revision gap | An app is worked on in a cloud session and its `verify` fails on missing browsers. Then decide whether `sync` writes the hook into `.claude/` (it already owns the agent files there) or `docs/create-an-app.md` says how to add it |
| **Phone width is asserted, not designed.** The `mobile-chrome` project proves the app works at 393px, but that is inherited from shadcn, not chosen. 3.22 eased the worst of it (less-used filters behind `SecondaryFilters`, a pinned first column capped at 45% of the screen), but every column past the second is still off-screen with no column-visibility or density control | An app is genuinely used on a phone and someone complains. Decide first between "usable at 393px" (today) and "designed for 393px" (column priority, density, a card layout) |

## Excluded

- **Per-app edits to package components.** Configure through props, build
  on top, or raise the change here (`consuming.md` "Changing the
  foundation").
- **Custom primitives.** shadcn's are the base; the package patches them
  where needed.
- **Theme switcher UI.** Build the token architecture, not the feature.
- **SSR / SEO tooling.** Irrelevant for personal database applications.
