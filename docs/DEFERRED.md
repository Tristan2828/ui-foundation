# Deferred and Excluded

Out-of-scope ideas land here, never in code. See `docs/BUILD-PLAN.md` for the
full rationale behind each row.

A row is **removed when it ships** — this is a queue of what is left, not a
log of what was done. 26 rows were drained on 2026-09-27/28 (semantic
tones, the cell-pattern catalogue, the column-options step, the release

## Direction (decided 2026-09-20, while building the Game List app)

Set by the developer, and it supersedes the "don't extend speculatively" framing wherever the two conflict. Rows below marked **Met** or **Decided** follow from it.

- **Two tracks.** *Design language* — tokens, semantic tones, `Badge`/variant styles, cell patterns, typography, density, themes — grows freely and does not wait for a second app or a second use. *Structure* — composites, new registry items, backend, auth, infrastructure — stays need-driven: built against a real app, not in advance. Why the split: design language is cheap to review by looking at results and is exactly what a consuming app cannot get right alone (contrast, both themes, consistency); structure is where "building forever" is a real risk.
- **The "basic" look was a v1 leftover, not a design position.** BUILD-PLAN's non-goal ("This foundation does not need to be good. It needs to be reusable. Polish is what the first real application is for") and its v1.0 scope budget (exactly three composites, three registry items, six field types) were ship guards. v1 shipped, a real application now exists, and it wants polish — so both stop capping design-language work.
- **Review model.** The developer reviews *results* (the running app, the per-column options pages), not every line of code. Mechanical gates remain the safety net; the goal is a foundation strong enough that line-by-line review isn't needed. See the "Docs that still describe the old stance" row.
- **Process ceremony is negotiable.** The consume-test/tag/README release routine and the pixel screenshot baselines are up for slimming or replacement — see the two process rows.
- **Unchanged:** the Hard Rules (semantic tokens only, shadcn before hand-rolling, gateway boundaries, dependency allowlist). Every design-language addition still ships with axe contrast coverage in both themes. Stronger tokens make the token rule more useful, not less.

| Categorical (non-status) color tokens — a palette for values that differ from each other but aren't better or worse, e.g. Game List's Genre column (Survival / ARPG / Shooter / Build / Army / Action / RPG). The status-color item above covers tones that *mean* something (success / warning / destructive); this is a separate need, and `theme.css` has nothing for it (`--chart-1..5` are grays). Game List built its own: per genre a `--genre-<name>-700` (light) and `-400` (dark) primitive at one oklch hue, a semantic `--genre-<name>` remapped in `:root`/`.dark`, and a `--color-genre-<name>` line in `index.css`'s `@theme inline` — 35 lines across two files for one column, repeated for every new enum value or categorical column. Non-obvious bits a future agent would get wrong: (1) hues must avoid red and green, which success/destructive already spend, or a genre drawn in red reads as "bad"; (2) the tint goes on the glyph only and the label stays `text-foreground`, so contrast never depends on the hue — but axe checks text, not icon (non-text, 3:1) contrast, so the shades (oklch L 0.5 light / 0.78 dark, chroma ~0.12–0.15) were picked by eye and nothing automated covers them; (3) Tailwind needs whole class names, so the cell maps enum → `'text-genre-survival'` in a `Record` rather than building the class from the value; (4) with seven values, three hues land close together (violet / magenta / pink at 285 / 320 / 350), so the glyph shape, not the hue, is what tells those genres apart. Idea for the foundation: generic slots (`--category-1..8`, the same two-layer shape as `--chart-*`, both themes, one `@theme inline` line each) that an app maps enum → slot in its columns file, instead of a token per enum value. Unproven — one column has needed it. Reference: `src/styles/theme.css`, `src/index.css` and the `genre` column in `src/routes/games/games-columns.tsx` in the Game List app, `master`, commit `906c7a4` (option 9 of 19 on the Genre exploration page) | A second column wants categorical color, or the status-color tokens item above gets actioned — design categorical slots in that same pass so "meaningful color" and "just distinct color" are decided together. Don't add per-enum tokens to the foundation; add slots or nothing |
| **Replace pixel screenshot baselines with programmatic checks.** The Storybook screenshots of the patched primitives (`playwright.storybook.config.ts`) and the dark-mode kitchen-sink `toHaveScreenshot` spec exist to catch hardcoded colors the ESLint token rule cannot see (inline styles, SVG fills). Cost: baselines must be generated in the CI container (a Windows or macOS baseline always fails CI), so every change needs a Linux round-trip through the CI artifact upload, and every new visual variant (three tones × outline/tinted/solid × two themes) multiplies the baselines to regenerate and review. Suggested replacement that keeps the detector: a Playwright test that renders each primitive and variant in both themes and asserts computed `color`, `background-color`, `border-color` and SVG `fill` resolve to a token value rather than an arbitrary color, alongside the existing axe contrast runs — same failure covered, no images, runs on any OS. Prove it with a negative control (introduce an inline hex, watch it fail) before deleting the baselines; then delete the "Screenshot baselines need a Linux round-trip" bullet from ARCHITECTURE's learned-the-hard-way list | Same session as the release-process row; do it before the semantic-color batch so the new variants are never given baselines |
| **`build:real` and `.env.real` never reach a consuming app.** The registry ships files and npm dependencies but can't merge `package.json` scripts, so `docs/add-an-entity.md` Step 0 adds exactly three (`gen:api`, `verify:fast`, `verify`) and this repo's `"build:real": "tsc -b && vite build --mode real"` never arrives; `.env.real` (the one-line `VITE_API=real` file that script loads) isn't in `registry.json`, `scripts/create-app.sh` or Step 0 either. `docs/deploy.md` tells the reader to run `npm run build:real`, so an app made by `create-app.sh` follows a doc for a script it doesn't have. The failure is quiet: `VITE_API` is baked in at build time, so a plain `npm run build` ships MSW and mock data. The Game List app serves its `dist/` from its FastAPI backend on `:8000`, so it showed the mock fixture (or a stale bundle) where real data was expected, and the developer only found out by asking whether an npm script existed — the mock-mode banner row above is the other half of the same confusion. Fixed locally in the Game List app: `package.json` script plus `.env.real`, verified by `npm run build:real` producing a `dist/` with no MSW chunk (`master`, commit `07f29c9`). Fix here: make Step 0 add `build:real` as a fourth script, and have Step 0 (or `create-app.sh`) write `.env.real` with the same header comment, so every new app gets both; keep the `!.env.real` exception in `.gitignore` wherever an app ignores `.env.*`, since the file is not a secret and must be committed. Found while building the Game List app with a separate agent | Next time `create-app.sh` or Step 0 is touched, or the next new app is created — add both then, and update `docs/create-an-app.md` (its step 3 lists the scripts Step 0 adds) and the consume-test so a fresh app is checked for `npm run build:real` producing a bundle without the MSW browser chunk. Small and concrete, not a design decision |
| **Fixture uniformity hides every "unset" path — a testing convention, not a one-off.** Every mock game in the Game List app fills in all four of its optional enums; no fixture has more than one null. That is why its create/edit form could ship a visible `__unset__` in four fields with `verify` green: no test ever loaded a record with those fields empty, and the create screen's default state was asserted only for the fields that had explicit coverage. The same shape is here — `src/mocks/data.ts`'s widgets are uniformly populated, and `Widget.assigneeEmail` is the single nullable field carrying the whole "empty-state display" job. The Required States rule already says every data *view* handles loading/empty/error/success; the gap is that "empty" is only ever tested at the **screen** level (no rows), never at the **field** level (a row whose optional fields are unset). Suggested convention, cheap and mechanical: every entity's mock data includes one deliberately sparse row with every optional field null, `docs/entities/_template.md` says so at its "Required" column, and `add-an-entity.md`'s test step asserts that row renders on both the table and the edit form. Game List's fix had to force such a record through an MSW override because no fixture could supply one. Found while reviewing that app's UI before porting work to this repo | Same session as the `<SelectValue>` row above — that defect is the worked example, so write the convention while the evidence is in hand. Start with the sparse-fixture rule alone; the template and playbook wording can follow. Worth checking at the same time whether `tests/mocks/conformance.test.ts` can assert the sparse row exists, which would make it a gate rather than a habit |

| **The `<nav>` landmark does not contain the nav at phone width.** `app-shell.tsx` wraps `<Sidebar>` in `<nav aria-label="Primary">`, but below the sidebar's mobile breakpoint the sidebar renders into a Sheet that is *portaled to document.body* — so the links land outside the landmark, which is then an empty `<nav>`. axe does not flag it (an empty landmark is legal, and the links are reachable and labelled), and the new `mobile-chrome` Playwright project passes with zero violations, so this is a semantics quirk rather than a defect. Fixing it means either moving the `<nav>` inside the sidebar's own content or dropping the wrapper and letting the sheet carry the landmark — both touch a registry-shipped file and a shadcn-owned one, so it wants a deliberate look rather than a drive-by. `e2e/a11y.spec.ts` documents the behaviour and reads the links from the sheet on mobile. Found while adding the phone-width project | Someone changes `app-shell.tsx`'s nav markup for another reason, or a screen-reader pass on a phone is actually done. Don't fix it blind — confirm first how it reads in a real mobile screen reader, since the current shape may well be fine in practice |
| **Phone-width is asserted, but nothing is *designed* for it.** The new `mobile-chrome` project proves the app works at 393px — the sidebar becomes a sheet, the toolbar wraps, `DataTable` scrolls behind its pinned column — but all of that is inherited from shadcn, not chosen. `src/routes` and `src/components/app` still contain **zero** `sm:`/`md:`/`lg:` breakpoints. What a phone user actually gets: the whole first viewport is filters before any row appears, and every column past the second is off-screen with no column-visibility or density control. This is *structure*, so it stays need-driven | A consuming app is genuinely used on a phone and someone complains about the scrolling, not before. Decide the target first — "usable at 393px" (today) versus "designed for 393px" (column priority, a density toggle, or a card layout under a breakpoint). Only the second is real work, and it belongs to whichever app needs it |
| **The `mobile-chrome` project excludes `shell.spec.ts`, and nothing covers the sheet's own behaviour.** That spec asserts the persistent sidebar and its expand/collapse cookie, which below the breakpoint is a different component (a Sheet), not a narrower one — so running it there tested nothing meaningful. `a11y.spec.ts` opens the sheet and axe-checks it, but no test asserts the sheet *works*: opens on the trigger, closes on navigation, traps focus. Found while adding the phone-width project | The sheet breaks, or `shell.spec.ts` is touched for another reason. Small and self-contained whenever picked up |

## Excluded

- **npm package** — forfeits open-code editability, the reason for this stack
- **Custom primitives** — shadcn's are already yours to edit
- **Theme switcher UI** — build the token architecture, not the feature
- **SSR / SEO tooling** — irrelevant for personal database applications
