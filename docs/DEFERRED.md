# Deferred and Excluded

Out-of-scope ideas land here, never in code. See `docs/BUILD-PLAN.md` for the
full rationale behind each row.

## Deferred

| Item | Revisit when |
|---|---|
| Login rate limiting / lockout on repeated failed attempts | The app is exposed somewhere a brute-force attempt is a real threat model, not a personal/local deployment. **Still deferred as of Phase 11** (docs/phases/phase-11.md) — flagged there as a real gap self-service registration widens, not yet picked up |
| Additional themes | A second app needs a distinct look |
| Monorepo | Two or more consuming apps share a release cycle |
| TypeScript 7 (native compiler) | typescript-eslint, openapi-typescript and Storybook's react-docgen-typescript all support it. TS 7's package exposes no classic JS API (`require('typescript')` has only `version`), and all three are built on that API — typescript-eslint caps at `<6.1` even in its v9 alpha. The tsconfigs are already TS 7-clean (no `baseUrl`, which TS 7 drops). When revisiting, also drop the `openapi-typescript` → `typescript` entry in `package.json`'s `overrides` once openapi-typescript's own peer range covers the installed TypeScript |
| Read-only entity path in the playbook (`/new-entity` for a list/detail table with no create, edit or delete — today it always builds full CRUD, and the near-term focus is display tables; see `docs/ARCHITECTURE.md` "Focus") | The first real app needs a read-only table. Build it against that app's actual screen, not in advance |
| Notion API as a data source — a thin backend that serves `openapi.yaml` from a Notion database instead of Postgres (the choice is documented in `docs/consuming.md`) | A real project picks Notion as its source of truth. Build it against that project's actual database and property types, not a hypothetical one |
| Row virtualization | A table exceeds ~5k rows |
| `AppError` kinds for 403 (`forbidden`) and 409 (`conflict`) — today both render as the generic `server` error | A backend actually returns either. None does now: another user's widget is a deliberate 404 and a duplicate email is a 422. Considered and not built in audit Phase D (`docs/phases/audit-phase-d.md`) |
| Error reporting | An app is actually deployed |
| Dependency-allowlist enforcement for `backend/pyproject.toml`, mirroring `deps-allowlist.json`/`check-deps.mjs` on the npm side | The backend gains a second contributor/session where an unreviewed Python dependency is a real risk — Phase 8 pinned versions by hand with no mechanical gate |
| Column-level documentation convention for the Postgres backend — `COMMENT ON TABLE`/`COMMENT ON COLUMN` on every table, required whenever a column's meaning isn't obvious from its name/type. No existing convention (zero `COMMENT ON` usage anywhere in `backend/` today) and no mechanical check. Found while planning a Game List app whose `game_ratings` table needs to be understood by a second, context-free agent with direct read-write Postgres access and no view of `openapi.yaml` or this repo | That app's migration actually ships `COMMENT ON` for real (its own plan documents the convention and a Row-Level Security policy alongside it); once proven there, decide whether it graduates to a Hard Rule with a mechanical check across `backend/`, the way other Hard Rules are enforced |
| `app-shell.tsx`'s `SidebarHeader` brand text (`<span>UI Foundation</span>`, ~line 100) has no collapse-aware styling — collapsing the sidebar to its icon-only rail (`collapsible="icon"`) doesn't hide or truncate it, so the text overflows past the narrowed rail. Found while building the Game List app with a separate agent | Next session in this repo — small, concrete fix, not a design decision; pair with the password-visibility item below |
| No password-visibility toggle on `login.tsx`/`register.tsx`'s password `Input`s (plain `type="password"`, no show/hide). `lucide-react`'s Eye/EyeOff icons are already a dependency — no new package needed. Check shadcn's registry for an existing password-input pattern first (`AGENTS.md` Hard Rule: never hand-roll what shadcn already has) before composing one from `Input` + `Button`. Found while building the Game List app with a separate agent | Same session as the sidebar-collapse fix above |
| Default-sort support in `DataTable`/the entity playbook — `docs/entities/_template.md`'s "Default sort" field has no working reference. `Widget` doesn't use one, so nothing here demonstrates the trap: a caller-side fallback (`sorting.length > 0 ? sorting : DEFAULT_SORTING`) conflicts with TanStack's own sort cycle (asc → desc → unsorted) — the third click's "unsorted" is immediately overridden back to the same default, so the header looks stuck. Fix is an opt-in `enableSortingRemoval` prop on `DataTable` (default unchanged, so `Widget`'s table is unaffected) plus a note at the template's "Default sort" line. Found while building the Game List app with a separate agent | That app's own `Game` table actually ships a default sort (it does — "status desc") and hit this exact bug, fixed locally (`enableSortingRemoval: false` hardcoded there, not yet generalized as an opt-in prop here) |
| Zebra striping on `TableBody` — a subtle alternating row tint, scoped so the header row is never affected. Found while building the Game List app with a separate agent | Purely additive polish; validated in that app's 122-row Games table, low-risk to add whenever picked up |
| Persistent captions above each toolbar filter in `widgets-table.tsx` — a `Select`'s own placeholder text (e.g. "Status") disappears once a value is picked, losing which filter it is. Found while building the Game List app with a separate agent | Validated fix in that app; belongs in `widgets-table.tsx` itself (not a new shared component) since every entity's toolbar is copied from that file, per `add-an-entity.md` |
| `vitest`/`eslint` recursively scan into a nested git worktree under the project root (e.g. `.claude/worktrees/<name>`), failing `verify` on another session's in-progress files rather than ignoring them. Found while building the Game List app with a separate agent | Given this repo is built mostly by AI agents (`ARCHITECTURE.md`), a worktree existing under the project root during a session is a realistic, recurring scenario, not hypothetical — that app hit this and fixed it by adding both configs' directory to their `exclude`/`ignores` lists |
| No semantic status/success/warning color tokens — `theme.css` is grayscale plus `destructive`, and the Hard Rule bans palette colors, so a consuming app has no sanctioned way to color-code a value like a game's Status or review sentiment (green = playing, red = dropped). The existing `Badge` variants are the only signal, and `games-columns.tsx` already notes the shipped `destructive` badge fails AA contrast. Surfaced while exploring table label styles in the Game List app: a reference mock used solid/tinted green and red labels, and the only compliant answer was "grayscale badges, no color". Any addition needs a second, darker text shade per color in both themes (tinted fills can't reuse the fill color as text — red-500 on a near-white tint is ~3.8:1, under 4.5:1) plus axe coverage in `e2e/a11y.spec.ts` | A consuming app decides it actually wants color-coded labels. Ask for the display style first (see the exploration-step item below) so tokens are added for a chosen style, not speculatively |
| "Choose how each column displays" step in `docs/add-an-entity.md` — today the playbook takes an entity plan's fields and builds the columns, with no step for deciding how a value should look (plain text, badge, icon badge, meter, bucketed label…). A developer who doesn't have design opinions (the Game List author is a backend dev) had to run this ad hoc: an agent generated a shareable options page per column, rendering the same sample rows in each style using the app's own tokens, with a one-line tradeoff each, and the developer picked one. That worked well and is repeatable. Worth capturing as an optional playbook step or a `/explore-column` command, and could seed a small catalog of cell patterns (number, enum, count, date, link) that `games-columns.tsx`-style files copy from. First outcome: Max Players went from a bare number to an outline `Badge` with a `UsersIcon` (`src/routes/games/games-columns.tsx` in the Game List app, branch `claude/table-display-exploration-92652c`), matching the Mechanics chips | More columns get picked the same way in the Game List app — if a few settle on the same handful of patterns, extract those; if not, keep it as guidance only. Don't build the catalog from one column |
| Icon badge as a documented cell pattern (a `Badge variant="outline"` with a leading lucide icon, e.g. a count column: `<Badge variant="outline"><UsersIcon data-icon="inline-start" /><span className="tabular-nums">{n}</span></Badge>`). **Deliberately not a new component:** shadcn's `Badge` already sizes child `svg`s and pads for `data-icon="inline-start"|"inline-end"`, and the Hard Rules ban hand-rolling what shadcn has, so a wrapper would only duplicate it. What's missing is discoverability — nothing in `docs/` or the reference implementations shows an icon in a badge or says when to use one. Candidate homes: a cell-patterns note next to the column-display playbook step above, or a short example in `docs/add-an-entity.md`. Reference use: Max Players in the Game List app (`src/routes/games/games-columns.tsx`, branch `claude/table-display-exploration-92652c`) | Same session as the column-display playbook step above — write it as one of that step's catalog entries, not on its own |
| Icon-only cell as a documented pattern — an enum column shown as a glyph with no visible label (Game List's Controller Support column, chosen over eight other styles), with the label moved to a `Tooltip` and an `aria-label`. Two non-obvious bits a future agent would get wrong and nothing in `docs/` shows: (1) Base UI's `TooltipTrigger` renders a `<button>` by default — a read-only cell icon should instead use `render={<span role="img" aria-label={label} tabIndex={0} />}` so it is keyboard-focusable and named without being a fake button; (2) it depends on the `TooltipProvider` that `app-shell.tsx` already mounts, so it works in any table cell for free but not in an isolated Storybook story without one. Also documents the shape-not-color rule for such icons (fill level: solid / half / slashed / dashed) so the column still reads for a colorblind viewer, the same reasoning `games-columns.tsx` already gives for the Reviews icon. Deliberately not a component — the glyph is per-entity; only the wrapper markup is reusable. Reference: `src/routes/games/controller-support-icon.tsx` and its use in `games-columns.tsx` in the Game List app, `master`, commit `3e88422` (first shown as option 7 of 9 on the Controller Support exploration page) | Same session as the column-display playbook step and the icon-badge pattern above — write it as a third catalog entry ("icon only, label in tooltip") beside "icon in a badge". Icon-only is the choice a second column would repeat (Crossplay is the likely one), so wait for that before extracting anything |
| A third semantic tone: **warning/caution** (amber). The status-color item above covers success and destructive, and the Game List app has since added `success-text`/`destructive-text` tokens and `outline-success`/`outline-destructive` `Badge` variants locally (commits `02f3c4c`, `92d9724`). Ranking a three-tier value — Controller Support Full / Partial / None is the clean example — wants a middle tone; the app first reused `success-text` for Partial, leaning on the half-filled shape alone — and Partial rendered green like Full, which the developer flagged immediately. It now has a local `--warning-text` token (amber-700 light / amber-400 dark, exposed as `text-warning-text`; `src/styles/theme.css`, `src/index.css`, `master` commit f920a47) that passes the app's axe contrast checks in both themes; use those as the starting shades. Same requirement as the other tones: a darker text shade in both themes plus axe coverage before any color is added | The status-color item above gets actioned — add warning in the same pass so the three tones are designed together, or a consuming app hits a value that genuinely needs a middle color and the shape-only workaround stops being enough |
| Format of the per-column options page (extends the column-display playbook step above). The Controller Support page added two things beyond "same rows, N styles, one-line tradeoff each" that made choosing much faster and belong in the step's template: (1) a **"try it in a table" preview** — a switcher that re-renders one sample table (real column names, ~7 rows including a null) in the selected style, because a style that looks fine in an isolated card can be too noisy down 25 rows; and (2) a **cost line per option** stating what it trades away (extra text shade, ambiguity of blank, needs color, etc.). Numbered cards so the developer can reply "5". Known weakness worth solving when this is built: the page re-implements each cell renderer in vanilla JS with copied tokens, so it can drift from the app (e.g. it used an amber the app has no token for). Rendering the options from the app's real components — e.g. as Storybook stories, since Storybook is already in the repo — would remove that drift and let the winner be copied straight out | Same session as the column-display playbook step. Build the template from the pages of both columns explored so far (Max Players, Controller Support) plus any that follow; don't design it from this note alone |
| Link cell as a documented pattern — an external URL shown as a small outline button (`Button variant="outline" size="sm"` with `nativeButton={false}` and `render={<a href={url} target="_blank" rel="noreferrer" />}`, label "Open" plus a trailing `ExternalLinkIcon`), chosen over eight other styles (generic text link, store name from the domain, raw domain, icon-only, store badge, hover-reveal, open+copy, name-as-link). Non-obvious bits a future agent would get wrong: (1) the `render={<a />}` + `nativeButton={false}` form is what keeps it a real anchor styled as a button (a `<button>` wrapping an `<a>` is invalid, and Base UI warns without `nativeButton={false}`); (2) every row shows the same visible word "Open", so give each an `aria-label` naming the row (`Open ${name} store page`) — the visible text stays inside the accessible name; (3) the null case must render the shared em-dash `emptyCell`, not a disabled button. Cost of the choice: it is the loudest link style and reads as a wall of buttons down a long table — the alternatives (store name/badge) need a domain-to-name map the app would own. Reference: the `link` column in `src/routes/games/games-columns.tsx` in the Game List app, `master`, commit `3694aba` (option 6 of 9 on the Link column exploration page) | Same session as the column-display playbook step and the cell-pattern entries above — write it as the "link" entry of that catalog (the playbook step already lists link as a candidate pattern). Don't extract a component: it's ~10 lines of markup over shadcn's `Button`. Also a data point for the options-page template item: this page put an empty-value row in every mini table, which surfaced the null case for free — keep that in the template |

## Excluded

- **npm package** — forfeits open-code editability, the reason for this stack
- **Custom primitives** — shadcn's are already yours to edit
- **Theme switcher UI** — build the token architecture, not the feature
- **SSR / SEO tooling** — irrelevant for personal database applications
