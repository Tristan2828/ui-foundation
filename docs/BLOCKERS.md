# Blockers

Open items that couldn't be resolved within a session's scope, or that need
a human decision made in `docs/OPERATOR.md` terms. Resolved items are
removed once fixed — this file is a queue, not a log.

## `spec-tester` cannot be invoked as a real isolated subagent in this harness

**What:** `.claude/agents/spec-tester.md` exists (since Phase 0) with its
deny-hook declared in its own frontmatter, per the plan's explicit warning
that subagents don't inherit `.claude/settings.json` hooks. But the Claude
session used for Phases 0-2 runs inside a harness with a fixed built-in
agent roster (`claude`, `claude-code-guide`, `Explore`, `general-purpose`,
`Plan`, `statusline-setup`) that does not discover project-level
`.claude/agents/*.md` files at all — confirmed via the `claude-code-guide`
agent in Phase 2. This is not a project misconfiguration; it's a property
of this specific harness (not stock Claude Code CLI).

**Why it matters:** `spec-tester`'s whole value is context isolation — an
agent that mechanically cannot read `src/api/gateway/` or
`src/api/transport/` while writing tests against `openapi.yaml`. Without
being able to invoke it, that guarantee has no enforcer in this harness.

**What was done instead (Phase 2):** temporal isolation. The Phase 2
gateway tests (`tests/gateway/*.test.ts`) were written by a fresh
`general-purpose` agent, with no memory of this session, given only
`openapi.yaml`, `src/api/contracts.ts`, and `src/api/schema.d.ts`, and
instructed not to read anything under `src/api/gateway/` or
`src/api/transport/` — which at the time contained only `.gitkeep`
placeholders, so there was nothing to read even if it had tried. This is
weaker than context isolation (nothing mechanically prevents a future
session's test-writer from peeking) but was judged sufficient for now; see
`docs/phases/phase-2.md`.

**What needs a human decision:** whether to run Phase 0's optional-tier
unattended loop (`scripts/run-phase.sh`) at all in this harness, since it
assumes stock Claude Code's `Task` tool with custom subagents. If the
answer is "run phases from a stock Claude Code CLI session instead," this
blocker likely resolves itself the next time `.claude/agents/spec-tester.md`
is invoked from that environment — confirm with the same refusal test
described in `docs/phases/phase-0.md` before trusting it.

## Dark-mode screenshot baselines (Phase 3) were generated on win32, not CI's Linux container

**What:** `e2e/shell.spec.ts-snapshots/*.png` (11 files, one per kitchen-sink
section) were generated by running `npx playwright test --update-snapshots`
on this dev machine, which is Windows. Playwright's snapshot file naming
bakes in the platform (`kitchen-button-dark-chromium-win32.png`), and CI
(`.github/workflows/verify.yml`) runs on `ubuntu-latest`, which will look
for `kitchen-button-dark-chromium-linux.png` — a file that does not exist.

**Why it matters:** this is exactly the failure mode
`docs/BUILD-PLAN.md`'s Phase 3 warning calls out — "baselines captured on a
[non-Linux OS] will not match Linux CI... An agent that sees a permanently
red screenshot check learns to ignore the gate." The plan's prescribed fix
is `docker run --rm -v $(pwd):/work -w /work
mcr.microsoft.com/playwright:v4.21.0 npx playwright test
--update-snapshots`, generated inside the same container CI uses.

**What was done instead:** nothing — this session's environment has no
`docker` binary and no WSL distribution installed (confirmed:
`docker --version` → command not found; `wsl --list` → no installed
distributions), so there was no way to produce Linux-matching baselines.
The win32 baselines were committed anyway so the local `check-phase-3.sh`
gate (which does run in this environment) has something real to compare
against, and so the screenshot *mechanism* — sections render, dark mode
toggles, `toHaveScreenshot` captures each one — is proven working this
session rather than left entirely unbuilt.

**What needs a human decision / action:** the first push to `main` (or a
PR) will almost certainly fail `verify.yml`'s Playwright step with "A
snapshot doesn't exist" for all 11 `*-linux.png` files. Whoever has Docker
or a Linux machine available should either:
- Run the plan's exact command locally and commit the resulting
  `*-linux.png` files, or
- Let the CI run fail once, download the actual/diff images Playwright
  uploads as a run artifact, and commit those as the new baseline, or
- Add a one-off `workflow_dispatch` job that runs
  `playwright test --update-snapshots` on `ubuntu-latest` and commits the
  result back to the branch.

Either way, don't just re-run CI hoping it passes — the win32 baselines
will never match pixel-for-pixel with Linux font rendering, so this needs
one deliberate regeneration, not a retry.
